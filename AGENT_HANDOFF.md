## Этап 5 (2026-10-19, продолжение). Доступность/DNS/подсети/сканирование/группы/фильтры в «Компьютерах»

Автономная сессия Hermes Agent (без доступа к Claude Code CLI — лимит подписки исчерпан у пользователя). Задача —
крупная фича: многопротокольная доступность, DNS-резолвинг, фильтры/сортировка, избранное и пользовательские группы,
подсети и их сканирование, слияние найденного с AD, UI, демо-режим, тесты.

### Что сделано полностью

1. **CIDR-парсинг и расчёт диапазонов** — `Core/Util/Cidr.cs` (`Cidr.TryParse/Parse`, `IPv4Range`). Маскирует адрес до
   сети, считает network/broadcast/usable-диапазон, корректно обрабатывает `/22`, `/24`, `/25`, `/31` (point-to-point,
   оба адреса годны, без исключений) и `/32` (один адрес). 23 теста в `CidrTests.cs` — самые ценные тесты задачи,
   включая `/0` без переполнения `uint`, и выбраковку некорректного ввода (IPv6, лишние октеты, пустая строка и т. д.).
2. **Многопротокольная доступность** — `Infrastructure/Network/ComputerAvailabilityService.cs`
   (`IComputerAvailabilityService`), стиль скопирован с `OnlineStatusService` (параллелизм/таймаут/отмена), но:
   отдельные флаги `RdpAvailable/SmbAvailable/SshAvailable/IcmpAvailable`, статус `Checking` выставляется в момент,
   когда конкретный компьютер реально берётся в работу (`IComputerIndex.SetAvailability(id, isChecking:true)` в начале
   `WorkAsync`, до этого — `Unknown`), сбой одного протокола не роняет остальные (`SafeProbeAsync`). Новые настройки:
   `RdpPort/SmbPort/SshPort/CheckIcmp/CheckRdp/CheckSmb/CheckSsh/AvailabilityProbeTimeoutMs/AvailabilityParallelism/
   AvailabilityAutoRefreshMinutes` в `AppSettings`. ICMP — новый `IIcmpProbe`/`IcmpHostProbe`
   (`System.Net.NetworkInformation.Ping`) в `RemoteShadow.Windows.Hosts`. 14 тестов в
   `ComputerAvailabilityServiceTests.cs`.
3. **DNS/обратный DNS** — `IDnsResolverService`/`DnsResolverService` (`Dns.GetHostAddressesAsync`) и
   `IReverseDnsResolver`/`ReverseDnsResolver` (`Dns.GetHostEntryAsync`) в Infrastructure; результат — IP-адреса
   компьютера (`ComputerInfo.IpAddresses`), DNS-запись сама по себе не означает доступность — это отдельный шаг.
4. **Подсети и сканирование** — `SubnetDefinition` (название/CIDR/тип проверки/таймаут/параллелизм),
   `SubnetScanner`/`ISubnetScanner`: ICMP и/или TCP (общие порты 445/3389/22) по `ProbeKind`, параллелизм/таймаут из
   самой подсети, прогресс через `IProgress<ScanProgress>`, отмена через `CancellationToken`. Никогда не запускается
   сама по себе — только явным вызовом `ScanSubnetCommand` на странице. 13 тестов (`SubnetScannerTests.cs`,
   `DeviceMergeServiceTests.cs`).
5. **Слияние AD + скан** — `IDeviceMergeService`/`DeviceMergeService`: сопоставление по обратному DNS (короткое имя,
   регистронезависимо) с `Name`/`DnsName` компьютера AD, НЕ по IP. Конфликт (имя совпало у двух компьютеров AD) или
   отсутствие PTR — устройство остаётся несопоставленным («вне AD»). `DiscoveredDevice.Key` = IP в рамках подсети:
   повторный скан обновляет существующую запись, а не плодит дубликат; устройства, не найденные в последнем скане, не
   удаляются — помечаются `FoundInLastScan=false` (история подсети).
6. **Фильтры и сортировка** — чистая функция `Core/Util/ComputersFilter.cs` (`Apply`/`Sort`/`ApplyAndSort`),
   используется и во ViewModel, и в тестах напрямую (без WPF/индекса). Доступность (все/доступные/недоступные/
   непроверенные — `Unknown` включает `Checking`), источник (AD/скан/все), текстовые фильтры по имени/IP/описанию/OU
   (через И), чекбоксы RDP/SMB/SSH, «показывать отключённые», сортировка (доступность по умолчанию — доступные
   наверх, по имени, по IP, по времени проверки), возрастание/убывание. 16 тестов, включая smoke-тест на 6000
   сгенерированных компьютеров (`ComputersFilterTests.cs`) — укладывается в секунды, не часы.
7. **Избранное и пользовательские группы** — `ComputerGroup` (Id/Name/ComputerIds/DiscoveredDeviceKeys) в
   `AppSettings.ComputerGroups`, расширен существующий `FavoriteComputers`. Команды на странице: создать/переименовать
   (через `IDialogService.PromptTextAsync`)/удалить группу, добавить/убрать выбранный компьютер (может быть сразу в
   нескольких группах). Удаление группы не трогает AD — только список в настройках.
8. **Хранение настроек** — `AppSettings` расширен без поломки обратной совместимости: все новые поля
   nullable/default, `JsonSettingsStore.Normalize` подставляет пустые списки для старого файла без этих полей.
   `ComputerCacheFile`/`CachedComputer` — добавлено поле `IpAddresses` (кэшируется), доступность по протоколам
   намеренно НЕ кэшируется между запусками (должна быть актуальной, не унаследованной). 4 новых теста
   (`JsonSettingsStoreNetworkTests.cs`) плюс обновлён существующий `Null_lists_in_hand_edited_file_become_empty_lists`.

### Архитектурные решения и альтернативы (почему так)

- **Протокольные флаги и `Checking`/`Unknown`/`Online`/`Offline` — прямо в `ComputerInfo`**, а не в отдельной
  параллельной структуре, по аналогии с тем, как там уже жил `IsOnline`: один источник правды для UI-биндинга,
  `ComputerIndex.ApplyUpdates` расширен так же, как уже было для `IsOnline` (новые поля переживают обновление из AD).
  Альтернатива (отдельный словарь `Dictionary<Guid, Availability>` в индексе) усложнила бы и UI-биндинг, и слияние.
- **`IComputerAvailabilityService` — новый сервис рядом с `IOnlineStatusService`**, а не замена/рефакторинг
  существующего: `IOnlineStatusService` используется `ComputerIndex` в проде как есть и покрыт контрактными тестами
  (`ServiceRegistrationTests`); трогать его означало бы рисковать существующими 1724 тестами ради сервиса, который и
  так предполагался к расширению «рядом». Новый сервис переиспользует тот же `IHostProbe` и тот же стиль работы.
- **`ComputersFilter` — статический класс с чистыми функциями**, а не метод ViewModel: тестируется без WPF/DI,
  используется и в smoke-тесте на 6000 записей, и в самой странице — одна реализация вместо двух.
- **Группы/подсети — `List<T>` с мутируемыми классами в `AppSettings`**, по аналогии с уже существующим
  `List<Guid> FavoriteComputers`: тот же стиль хранения, та же (де)сериализация System.Text.Json, та же нормализация
  null-списков в `JsonSettingsStore`.
- **Слияние только по обратному DNS, не по IP** — требование ТЗ прямо об этом просит (IP может случайно совпасть или
  устареть в DHCP); реализовано как чистая функция (`DeviceMergeService.Match`), без побочных эффектов, легко
  тестируется на конфликтных кейсах.
- **Доступность не кэшируется на диске между запусками** (в отличие от списка IP, который кэшируется) — иначе при
  следующем запуске пользователь увидел бы доверенный, но давно устаревший статус «зелёный»/«красный».

### Что упрощено / не реализовано (честно)

1. **Дерево подразделений (OU) на «Компьютерах» по-прежнему нет** — пункт был открыт ещё с прошлого этапа и не входил
   явно в объём этой задачи; «дерево» в этой сессии — это сворачиваемая панель «Группы и подсети» (доступность/
   источник — выпадающие списки, группы/подсети — плоские списки с CRUD), а не полноценный `TreeView` с иерархией
   OU → группы → подсети → найденные устройства. Технической преграды нет, это вопрос объёма работы.
2. **Создание подсети — через поля на странице, а не модальный диалог** с отдельной формой: `IDialogService` в
   проекте не имеет метода «многополевой диалог», а добавлять его ради одной формы в условиях ограниченного времени
   не стали — посчитали нечестным тратить время на диалоговую обвязку в ущерб тестам и бэкенду. Функционально работает
   так же (название/CIDR/тип проверки/таймаут/параллелизм, валидация CIDR перед добавлением).
3. **Найденные сканированием устройства показаны отдельным списком**, а не влиты в одну виртуализированную таблицу с
   AD-компьютерами (они разных типов — `ComputerInfo` и `DiscoveredDevice`). Сопоставленные устройства (`MatchedComputerId`
   не null) подтверждают, что AD-компьютер отвечает в этой подсети, но это не отображается как отдельная колонка в
   основной таблице — только в разделе «Найдено сканированием».
4. **UI не проверялся вручную глазами** (только через 27 тестов `RemoteShadow.App.Tests` на реальном стеке
   Infrastructure+Modules+Demo и headless-запуск `--demo`, который подтвердил отсутствие `crash.log` и корректное
   наполнение `settings.json` демо-данными) — та же причина, что и в «Этапе 4»: автоматизация рабочего стола в этой
   среде не может кликать по окну WPF. Разделы и кнопки, добавленные в XAML, не прошли ручной клик мышью.
5. **История подсети (устройства, не найденные при последнем скане) хранится только в памяти ViewModel**
   (`_discoveredByKey`), не персистится в `AppSettings`/на диск между перезапусками программы — при перезапуске
   история начинается заново. `ComputerGroup.DiscoveredDeviceKeys` заведено в модели для будущей привязки найденных
   устройств к группам, но UI для этого (добавить найденное устройство в группу) не реализован.
6. **Автообновление доступности по таймеру** (`AvailabilityAutoRefreshMinutes`) — настройка есть и используется как
   TTL кэша в `ComputerAvailabilityService` (повторный ручной вызов в пределах интервала не пересчитывает уже
   проверенные записи), но сам периодический таймер, который бы сам нажимал «Обновить», не заведён — именно по
   требованию ТЗ «ручное обновление, не автозапуск для всей сети»; значение 0 по умолчанию означает «только вручную».
7. **Опрос «Найти пользователя» по подразделениям** (из «Этапа 4», пункт 1) и **дерево OU на «Компьютерах»/
   «Диагностике»** (пункты 2–3) — не изменились, остаются открытыми.
