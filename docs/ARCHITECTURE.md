# Архитектура RemoteShadow

RemoteShadow — настольная программа «пульт админа» для Windows-домена: shadow-подключение к сессиям пользователей, RDP/SSH, управление AD и диагностика в одном окне. Сначала Windows, потом, возможно, macOS.

Главные требования к архитектуре:

1. **Новую функцию добавляют, не трогая остальной код** — одним классом или одним скриптом.
2. **Программа работает и на доменном, и на недоменном компьютере.** Если компьютер не в домене, она спрашивает домен, логин и пароль администратора и выполняет все сетевые операции от его имени.
3. **Код, зависящий от Windows, изолирован**, чтобы позже собрать версию для macOS и запускать интерфейс в демо-режиме.

## Стек

| Что | Чем | Почему |
|---|---|---|
| Язык и платформа | C# / .NET 10 | Нативный доступ к Windows API (WTS, ADSI, LogonUser), один `.exe` |
| Интерфейс | Avalonia 11 + MVVM (CommunityToolkit.Mvvm) | Работает на Windows и macOS; интерфейс можно отлаживать на Mac |
| Внедрение зависимостей | Microsoft.Extensions.DependencyInjection | Модули регистрируют свои сервисы и действия |
| Работа с AD | System.DirectoryServices + AccountManagement (Windows), позже System.DirectoryServices.Protocols (macOS) | Сброс пароля, разблокировка, поиск — штатными средствами |
| Сессии | WTS API (P/Invoke `wtsapi32.dll`) | То же, что `qwinsta`/`quser`, но быстро и без парсинга текста |
| Shadow / RDP | `mstsc.exe` | Shadow умеет только mstsc (см. [исследование](research/)) |
| SSH | `ssh.exe` в Windows Terminal | Встроенный OpenSSH-клиент Windows |
| Тесты | xUnit | |
| Сборка | GitHub Actions на `windows-latest` | Готовый `.exe` как артефакт сборки |

## Проекты в решении

```
RemoteShadow.sln
├─ src/
│  ├─ RemoteShadow.Core          # Контракты и модели. Без зависимостей от ОС и UI
│  ├─ RemoteShadow.Windows       # Реализации для Windows: WTS, ADSI, LogonUser, mstsc
│  ├─ RemoteShadow.Demo          # Фейковые реализации с тестовыми данными (для Mac и скриншотов)
│  ├─ RemoteShadow.Modules       # Встроенные функции: каждая — отдельный модуль
│  └─ RemoteShadow.App           # Avalonia-оболочка: окна, навигация, диалоги, вход
└─ tests/
   └─ RemoteShadow.Core.Tests
```

Правило зависимостей: `App → Modules → Core ← Windows / Demo`. Модули знают только интерфейсы из Core, поэтому один и тот же модуль работает и с настоящим доменом, и в демо-режиме.

## Расширяемость: модули, действия, страницы

Каждая функция программы — **модуль**. Модуль регистрирует то, что он добавляет:

- **Действия (actions)** — кнопки и пункты контекстного меню для объекта: компьютера, сессии или пользователя. Например, «Shadow: управление», «Сбросить пароль», «Перезагрузить».
- **Страницы (pages)** — целые вкладки в навигации. Например, «Компьютеры», «Пользователи», «Журнал».
- **Сервисы** — всё, что нужно модулю внутри.

Оболочка сама собирает все действия и показывает их в нужном месте. Добавить функцию = добавить класс; правка интерфейса не нужна.

```csharp
// Core: контракты
public interface IModule
{
    string Id { get; }
    void Register(IServiceCollection services);
}

public interface IAction<TTarget>
{
    string Id { get; }
    string Title { get; }              // «Shadow: управление»
    string Group { get; }              // «Подключение», «Сессия», «AD» — группировка кнопок
    string? Icon { get; }
    bool IsDangerous { get; }          // true → спросить подтверждение
    bool CanExecute(TTarget target, ActionContext context);
    Task ExecuteAsync(TTarget target, ActionContext context, CancellationToken ct);
}

// Цели действий
public sealed record ComputerTarget(ComputerInfo Computer);
public sealed record SessionTarget(ComputerInfo Computer, SessionInfo Session);
public sealed record UserTarget(UserInfo User);
```

`ActionContext` даёт действию всё нужное: текущее подключение к домену (`IDomainConnection`), диалоги (`IDialogService`), журнал (`IAuditLog`), запуск внешних программ (`IProcessLauncher`) и уведомления.

### Пример: как добавить новую функцию

Задача: кнопка «Открыть C$» для компьютера.

```csharp
public sealed class OpenAdminShareAction : IAction<ComputerTarget>
{
    public string Id => "computer.open-admin-share";
    public string Title => "Открыть C$";
    public string Group => "Файлы";
    public string? Icon => "folder";
    public bool IsDangerous => false;

    public bool CanExecute(ComputerTarget t, ActionContext ctx) => t.Computer.IsOnline;

    public Task ExecuteAsync(ComputerTarget t, ActionContext ctx, CancellationToken ct)
    {
        ctx.Audit.Write("open-admin-share", t.Computer.Name);
        return ctx.Launcher.StartAsync("explorer.exe", [$@"\\{t.Computer.DnsName}\C$"], ct);
    }
}

// регистрация в модуле
services.AddAction<ComputerTarget, OpenAdminShareAction>();
```

Кнопка появится на панели компьютера и в контекстном меню автоматически.

### Уровни расширения (по мере роста)

1. **Встроенные модули** (с первой версии) — классы в `RemoteShadow.Modules`.
2. **Скрипт-действия** (фаза 9) — папка `scripts/` рядом с `.exe`. Каждый `.ps1` с заголовком-метаданными (название, цель, группа, опасное ли) становится кнопкой без перекомпиляции. Программа передаёт в скрипт имя компьютера, ID сессии или логин пользователя.
3. **Плагины-DLL** (позже) — сборки из папки `plugins/`, которые загружаются через `AssemblyLoadContext` и регистрируют свои `IModule`.

## Подключение к домену и учётные данные

### Два режима

| Режим | Когда | Как работает |
|---|---|---|
| **Текущий пользователь** | Компьютер в домене и вы вошли доменной учётной записью | Всё через Kerberos от вашего имени, пароль не нужен |
| **Явные учётные данные** | Компьютер не в домене, или вы хотите работать под другой учётной записью | Окно входа: домен, контроллер домена (необязательно), логин, пароль |

При запуске программа проверяет, состоит ли компьютер в домене (`NetGetJoinInformation`). Если нет — сразу показывает окно входа. Если да — работает от текущего пользователя, а в меню есть «Войти под другой учётной записью».

### Окно входа

- **Домен** — например `corp.local`. Контроллер домена находится автоматически через DNS (`_ldap._tcp.dc._msdcs.<домен>`), но его можно указать вручную.
- **Логин** — `CORP\admin` или `admin@corp.local`.
- **Пароль.**
- **Запомнить** — сохраняет логин всегда, а пароль только по отдельной галочке, в Диспетчере учётных данных Windows (шифрование DPAPI, привязано к вашей учётной записи Windows).
- Перед входом программа проверяет учётные данные пробным подключением к LDAP и сразу говорит, если пароль неверный или контроллер домена недоступен.

### Как учётные данные применяются

Все сетевые операции идут через одну абстракцию `IDomainConnection`, поэтому модули не знают, в каком режиме работает программа.

| Операция | Текущий пользователь | Явные учётные данные |
|---|---|---|
| LDAP (поиск, сброс пароля, группы) | Kerberos от текущего пользователя | `DirectoryEntry` / `PrincipalContext` с логином и паролем, LDAP с подписью и шифрованием |
| WTS (сессии), удалённый реестр, перезагрузка | Как есть | Внутри `WindowsIdentity.RunImpersonated` с токеном `LogonUser(LOGON32_LOGON_NEW_CREDENTIALS)` — аналог `runas /netonly`: локально вы — это вы, в сети — администратор домена |
| mstsc (shadow, RDP), ssh, другие программы | Обычный запуск | `CreateProcessWithLogonW` с флагом `LOGON_NETCREDENTIALS_ONLY` — процесс получает сетевые учётные данные администратора |

Пароль хранится в памяти только на время работы программы и никогда не пишется в журнал, файлы настроек или аргументы командной строки.

### Требования к недоменному компьютеру

- DNS должен разрешать имена домена: DNS-сервер указывает на контроллер домена, или подключён VPN с доменным DNS.
- Доступны порты: 389/636 (LDAP), 88 (Kerberos), 445 (SMB/RPC — сессии и shadow), 3389 (RDP), динамические порты RdpSa для shadow.
- Если Kerberos недоступен, Windows откатится на NTLM; это работает, но в защищённых доменах NTLM может быть запрещён.

## Демо-режим

Если программа запущена не на Windows, или с ключом `--demo`, вместо `RemoteShadow.Windows` подключается `RemoteShadow.Demo`: тестовый домен с подразделениями, компьютерами, пользователями и сессиями. Так интерфейс можно разрабатывать и проверять на Mac, а скриншоты для документации не раскрывают реальные данные.

## Журнал аудита

Каждое действие пишется в журнал: время, кто (учётная запись администратора), что, над чем, результат. Формат — JSON Lines в `%AppData%\RemoteShadow\audit\yyyy-MM.jsonl`. Журнал виден на отдельной вкладке. Пароли и другие секреты в журнал не попадают никогда.

## Безопасность

- Пароль администратора — только в памяти и, по желанию, в Диспетчере учётных данных Windows.
- Опасные действия (выход пользователя, перезагрузка, сброс пароля) требуют подтверждения.
- Shadow без запроса пользователю работает, только если это разрешено групповой политикой `Shadow` на целевом компьютере. Программа это не обходит, а диагностика показывает текущее значение.
- Внешние программы запускаются со списком аргументов, без `cmd /c`, а имена компьютеров проверяются перед передачей в `mstsc` или `ssh`.
