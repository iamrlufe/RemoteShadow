# Собираем пульт админа домена из готовых блоков

Готового продукта, который одновременно делает shadow-подключение к сессии пользователя, браузерный RDP/SSH к серверам, управление AD и диагностику, нет. Лучший путь — **написать собственный тонкий портал и подключить к нему готовые компоненты**. Портал — это ASP.NET Core + Blazor на доменном Windows Server под gMSA. Браузерный RDP/SSH и запись сессий берутся из Apache Guacamole. Shadow делается через **Windows jump host с `mstsc /shadow`**. AD и машины управляются через LDAP с шифрованием и WinRM + JEA. Главное ограничение задаёт shadow. Современный механизм `mstsc /shadow` работает через недокументированный RPC-вызов `RpcShadow2`, и **его реализует только mstsc.exe**. Ни FreeRDP, ни Guacamole, ни IronRDP, ни клиенты для macOS не умеют подключаться к уже открытой сессии. Поэтому админ на Mac может сделать shadow только «через Windows»: удалённо открыть сессию на jump host и запустить mstsc там. Если такое ограничение неприемлемо, можно взять агент, который снимает экран (MeshCentral). Но это уже не RDP shadow, а отдельный агент на каждой станции. Второе ограничение касается безопасности. Портал, который сбрасывает пароли, меняет группы и читает пароли LAPS, по модели Microsoft относится к **control plane (Tier 0)**. Его хост, учётная запись, база и конвейер сборки защищаются как контроллер домена. Если нужно «завтра», есть готовая связка: Devolutions RDM ($30 за пользователя в месяц) или Royal TSX для подключений плюс LizardSystems TSM на jump host для shadow. Собственный MVP займёт, по моей оценке, **6–10 недель** работы одного разработчика.

## Shadow живёт только в mstsc.exe, и это задаёт всю архитектуру

Современный shadow (с Windows 8.1 / Server 2012 R2) не является обычным RDP-подключением на порт 3389. mstsc открывает SMB named pipe `\pipe\SessEnvPublicRpc` на **TCP 445** и вызывает единственную функцию `RpcShadow2` интерфейса `1257b580-ce2f-4109-82d6-a9459d0bf6bc`, которую хостит служба SessionEnv. Затем TermService запускает в сессии пользователя `RdpSaProxy.exe` и `RdpSa.exe`, и mstsc подключается к ним на **динамическом высоком порту** ([BITSADMIN](https://blog.bitsadmin.com/spying-on-users-using-rdp-shadowing); [FreeRDP #5656](https://github.com/FreeRDP/FreeRDP/issues/5656)). Microsoft документирует только командную строку: `mstsc /v:<host> /shadow:<sessionID> [/control] [/noConsentPrompt] [/prompt]` ([Microsoft Learn: mstsc](https://learn.microsoft.com/en-us/windows-server/administration/windows-commands/mstsc)). Сам RPC-интерфейс найден реверс-инжинирингом. Мейнтейнер FreeRDP предлагает начинать его реализацию со спецификации MS-TSTS, а запрос на поддержку shadow в FreeRDP **открыт с октября 2019 года, и PR по нему нет** ([FreeRDP #5656](https://github.com/FreeRDP/FreeRDP/issues/5656)). В Remmina и rdesktop такие же запросы висят открытыми ([Remmina #2774](https://gitlab.com/Remmina/Remmina/-/issues/2774); [rdesktop #141](https://github.com/rdesktop/rdesktop/issues/141)). В README IronRDP shadow не упоминается вообще ([IronRDP](https://github.com/Devolutions/IronRDP/blob/master/README.md)). `freerdp-shadow-cli` — это другое: сервер, который транслирует локальный X11-рабочий стол. С mstsc и Guacamole он не работает ([FreeRDP #8744](https://github.com/FreeRDP/FreeRDP/issues/8744)).

Отсюда главное архитектурное следствие: **браузер и macOS сами начать shadow не могут**. По данным itopia, shadow требует клиента Remote Desktop Connection (mstsc) на Windows, а Store-приложение и клиенты для других ОС не поддерживаются ([itopia](https://helpcenter.itopia.com/en/articles/4809369-user-session-shadowing-support)). Явного заявления Microsoft о том, что Windows App для macOS не умеет `/shadow`, не нашлось, но и признаков такой функции нет. Коммерческие менеджеры подключений устроены так же. Royal TS запускает внешний mstsc, потому что, по словам самого вендора, у RDP ActiveX-контрола нет API для shadow ([Royal Apps community](https://community.royalapps.com/t/shadow-rds-sessions-directly-from-dashboard/369)). Devolutions RDM открывает shadow из Terminal Services console тоже через mstsc ([Devolutions forum](https://forum.devolutions.net/topics/12920/enumerate-and-shadow-remote-rds-sessions)). LizardSystems TSM тоже просто запускает mstsc с нужными флагами ([LizardSystems handbook](https://lizardsystems.com/terminal-services-manager/help/handbook/managing-user-sessions/shadowing-a-user/)). Есть обходной путь через Windows Remote Assistance: у него открытая спецификация MS-RAI, и FreeRDP умеет открывать приглашения `.msrcIncident` ([MS-RAI](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-rai/959fd78d-e085-4776-bad1-89e531c42c91); [FreeRDP #5287](https://github.com/FreeRDP/FreeRDP/issues/5287)). Но unsolicited-режим требует отдельной политики. Кроме того, по сообщению одного блога, после январских обновлений 2026 года файлы приглашений перестали открываться ([deyda.net](https://www.deyda.net/index.php/en/2026/02/05/workaround-after-remote-assistance-error/)). Источник единственный, но строить на этом продукт не стоит.

На целевых машинах shadow настраивается групповой политикой «Set rules for remote control of Remote Desktop Services user sessions» (DWORD `Shadow` в `HKLM\SOFTWARE\Policies\Microsoft\Windows NT\Terminal Services`). Значения: **0** — запрещено, **1** — полный контроль с согласием (действует и тогда, когда политика не задана), **2** — полный контроль без согласия, **3** — просмотр с согласием, **4** — просмотр без согласия ([woshub](https://woshub.com/rdp-session-shadow-to-windows-10-user)). Если политика требует согласия, `/noConsentPrompt` завершается ошибкой ([woshub](https://woshub.com/rds-shadow-how-to-connect-to-a-user-session-in-windows-server-2012-r2)). Значит, вопрос «спрашивать ли пользователя» решается на стороне Windows, а не в портале. Это плюс для соответствия требованиям. Ещё нужны запущенная служба TermService и права: локальный администратор или разрешение `WINSTATION_SHADOW` на листенере RDP-Tcp ([BITSADMIN](https://blog.bitsadmin.com/spying-on-users-using-rdp-shadowing)). В брандмауэре нужны SMB-In и предопределённое правило «Remote Desktop - Shadow (TCP-In)» для RdpSa.exe ([woshub](https://woshub.com/rdp-session-shadow-to-windows-10-user)). Shadow подключается к консольной сессии рабочей станции (обычно ID 1) **без выкидывания пользователя**. Если сессия заблокирована или на экране UAC, админ видит чёрный экран с паузой. Журнал `TerminalServices-RemoteConnectionManager/Operational` пишет события **20508/20503/20504** (согласие, начало и конец shadow), и их стоит собирать в аудит ([woshub](https://woshub.com/rdp-session-shadow-to-windows-10-user)). Источники расходятся в том, обязателен ли `AllowRemoteRPC=1`: Microsoft Q&A связывает с ним ошибку 1722, BITSADMIN считает, что достаточно TermService ([Microsoft Q&A](https://learn.microsoft.com/en-us/answers/questions/118448/rds-farm-error-1722-when-shadowing-session)). Это нужно проверить в своей лаборатории.

### Три рабочих способа доставить shadow админу на Mac

**Первый и рекомендуемый способ — Windows jump host.** Это RDS-сервер или админская VM, где mstsc запускается с `/shadow`. Портал выдаёт кнопку «Shadow», которая открывает RDP-сессию на jump host. Открыть её можно в браузере через Guacamole или в Windows App на Mac. В этой сессии mstsc запускается как RemoteApp с аргументами `/v:<host> /shadow:<id> /control`. В Guacamole 1.6.0 исправлены как раз ошибки RemoteApp: чёрный экран у неопубликованных приложений и недоступные свёрнутые окна ([Guacamole 1.6.0](https://guacamole.apache.org/releases/1.6.0/)). Один сторонний блог сообщает о проблемах совместимости RemoteApp с новыми сборками FreeRDP ([51sec](https://blog.51sec.org/2025/12/upgrade-freerdp-to-2117dfsg1-6deb12u1.html?m=0)), так что этот путь нужно проверить в лаборатории в первую очередь. Важная деталь: при `/shadow` mstsc **игнорирует учётные данные, сохранённые через cmdkey**, и работает от имени пользователя текущей сессии ([Royal Apps support](https://support.royalapplications.com/support/discussions/topics/17000022823)). Поэтому каждый админ должен входить на jump host под своей учётной записью, а не под общей. Тогда атрибуция в журналах Windows сохраняется. Сетевой доступ (445 и динамические порты RdpSa) нужен только от jump host к станциям, а с Mac — только до jump host.

**Второй способ — обработчик URL-схемы на Windows-машинах админов**, например `adcc://shadow?host=…&id=…`. Он запускает локальный mstsc. Microsoft прямо предупреждает, что такие обработчики получают данные из недоверенных источников ([Microsoft Learn: URI scheme](https://learn.microsoft.com/id-id/previous-versions/windows/internet-explorer/ie-developer/platform-apis/aa767914(v=vs.85))). Поэтому хост и ID сессии нужно проверять по белому списку, процесс запускать через CreateProcess с массивом аргументов, без `cmd /c`, а ссылку снабжать короткоживущей HMAC-подписью от портала. Для Mac этот способ не подходит, но полезен, если в команде есть Windows-админы.

**Третий способ — агентский захват экрана.** Так работает MeshCentral (Apache-2.0, релиз 1.2.6 от сентября 2026). Его агент показывает текущую локальную сессию пользователя, а не открывает новую ([MeshCentral #36](https://github.com/Ylianst/MeshCentral/issues/36)). Если на машине открыта RDP-сессия, агент предлагает выбрать между консолью и RDP-сессией. Согласие настраивается флагами DesktopPromptUser/DesktopNotifyUser на уровне сервера, группы устройств или пользователя ([MeshCentral #6710](https://github.com/Ylianst/MeshCentral/issues/6710); [DeepWiki](https://deepwiki.com/Ylianst/MeshCentral/8-security-and-authentication)). Это настоящий «вижу экран пользователя» в браузере на Mac без jump host, но у него есть известные проблемы. В открытом issue (октябрь 2025) делегированный не-админ может перехватить существующую RDP-сессию без запроса ([#7397](https://github.com/Ylianst/MeshCentral/issues/7397)). Кроме того, просматриваемую RDP-сессию через какое-то время выбрасывает на экран входа ([#6651](https://github.com/Ylianst/MeshCentral/issues/6651)). Ещё одна разница: согласие в агентских инструментах задаёт администратор сервера, а не GPO на конечной точке. Это слабее и требует отдельного аудита.

### Как найти сессию и пользователя

Чтобы получить ID сессии, нужен WTS API (`WTSOpenServer` → `WTSEnumerateSessionsEx` → `WTSQuerySessionInformation`). Это тот же MS-TSTS RPC, которым пользуются `qwinsta`/`quser`. Он работает через pipe `\PIPE\LSM_API_service` на 445 и требует права Query Information, которое по умолчанию есть у Administrators ([WTSEnumerateSessionsEx](https://learn.microsoft.com/en-us/windows/win32/api/wtsapi32/nf-wtsapi32-wtsenumeratesessionsexw); [MS-TSTS](https://learn.microsoft.com/en-us/openspecs/windows_protocols/ms-tsts/4f5ff568-2887-4c50-8b36-38bb85170b58)). Вызовы WTS синхронные, а выключенные машины отвечают долгими RPC-таймаутами (ошибка 1722) ([IBM](https://www.ibm.com/support/pages/node/240899)). Поэтому опрос строится как пул воркеров: быстрая проверка порта 445 и кэш. Опрашивать на лету сотни станций, чтобы ответить на вопрос «где сейчас пользователь X», плохо масштабируется. Надёжнее логон-скрипт или агент, который при входе и выходе пишет в портал пару «пользователь ↔ хост ↔ сессия». Сверять её можно с событием 4624 на конечной точке (типы 2/7/10/11) и с событием 4768 на DC ([Microsoft: 4624](https://learn.microsoft.com/en-us/previous-versions/windows/it-pro/windows-10/security/threat-protection/auditing/event-4624); [ManageEngine KB](https://www.manageengine.com/products/active-directory-audit/kb/how-to/how-to-check-domain-user-logon-history.html)). .NET-обёртка Cassia удобна, но её README заканчивается на Windows 10 / Server 2016 ([Cassia](https://github.com/danports/cassia)). Проще написать собственный P/Invoke на несколько функций.

## Готовые продукты закрывают куски, но не весь пульт

Все рассмотренные продукты делятся на два лагеря. **Агентские RMM и remote-support** (MeshCentral, Tactical RMM, RustDesk, Aspia) видят экран пользователя, но не являются RDP/SSH-шлюзами для серверов в полном смысле. **Шлюзы и бастионы** (Guacamole, JumpServer, Warpgate, Next Terminal, Teleport, WAC) проводят RDP/SSH из браузера, но всегда открывают *новую* сессию и **не умеют shadow**. Для Guacamole это видно из рассылки 2019 года и из отсутствия функции в 1.6.0 ([Apache list](https://lists.apache.org/thread/wq4x9g8zvdwn1c61yfpy09443zd6q2c8)). У WAC Remote Desktop умеет только «начать, отключить, Ctrl+Alt+Del» ([Microsoft Learn: WAC](https://learn.microsoft.com/en-us/windows-server/manage/windows-admin-center/use/manage-servers)). Управление AD в готовом виде есть в WAC (расширение в preview), в Devolutions RDM (AD dashboard) и в ManageEngine ADManager Plus.

Из готовых продуктов к «одному окну» ближе всех **Devolutions RDM для Windows**. Но shadow в RDM нельзя встроить в окно приложения. Он требует Windows и ломается при некоторых режимах учётных данных ([Devolutions forum](https://forum.devolutions.net/topics/37959/remote-session-shadow)). Новая функция «session shadowing» в RDM 2025.2 — это просмотр сессий, которые идут *через* Devolutions Gateway. К консоли пользователя за рабочей станцией она не подключается ([Devolutions blog](https://devolutions.net/blog/whats-new-in-remote-desktop-manager-20252/)). Для helpdesk лучше всего задокументирован LizardSystems TSM. Он ищет сессию сразу по нескольким серверам и даёт режимы View, Control и «Prompt for user consent». Официально вендор указывает целевые системы Server 2012 R2+, поддержка рабочих станций им прямо не заявлена ([LizardSystems handbook](https://lizardsystems.com/terminal-services-manager/help/handbook/managing-user-sessions/shadowing-a-user/)). RDCMan и mRemoteNG shadow не умеют вовсе ([Microsoft Learn: RDCMan](https://learn.microsoft.com/en-us/sysinternals/downloads/rdcman); [mRemoteNG issues](https://github.com/mRemoteNG/mRemoteNG/issues?q=shadow)).

Готовые open-source веб-порталы для AD — LDAP Account Manager, ad-webmanager (Flask) и GNU-ADMW (Django) — покрывают только CRUD объектов. Сессий, shadow, RDP и нормального аудита в них нет ([LAM manual](https://ldap-account-manager.org/static/doc/manual/pr01.html); [ad-webmanager](https://github.com/gombee/ad-webmanager)). Как основа они не годятся, хотя отдельные идеи из них стоит взять: связку «AD-группа → роль» и настраиваемые колонки атрибутов.

## RDP и SSH в браузер лучше взять у Guacamole, а не писать самому

Apache Guacamole 1.6.0 (июнь 2025) — самый зрелый встраиваемый шлюз. В этой версии появились FreeRDP 3, переписанный оптимизатор протокола guacd, улучшенный GFX/RemoteFX, проверка отпечатка сертификата RDP, SSH-сертификаты и улучшенный плеер записей ([Guacamole 1.6.0](https://guacamole.apache.org/releases/1.6.0/)). Для портала важнее всего **аутентификация через подписанный и зашифрованный JSON**. Портал формирует подписанный JSON с протоколом и параметрами подключения, шифрует его AES-128 общим ключом `json-secret-key`, и Guacamole открывает сессию без своего экрана входа ([Guacamole: Encrypted JSON auth](https://guacamole.apache.org/doc/gug/json-auth.html)). Получается кнопка «RDP» в один клик, а пароли целевых машин не попадают в браузер. Для более плотной интеграции guacamole-common-js встраивается прямо в страницу портала. Под ASP.NET есть готовый образец guacamole-sharp с .NET-бэкендом ([guacamole-sharp](https://github.com/m-expunged/guacamole-sharp); [guacamole-common-js](https://guacamole.apache.org/doc/gug/guacamole-common-js.html)). Запись RDP/SSH-сессий Guacamole даёт бесплатно, и это закрывает требование «видеть, что делал админ» без отдельного PAM. Нужно учитывать одну вещь: среди RDP-параметров Guacamole есть `console`, но **нет параметра shadow или ID сессии** ([Guacamole: Configuring](https://guacamole.apache.org/doc/gug/configuring-guacamole.html)). Поэтому shadow в Guacamole попадает только через RemoteApp на jump host.

Альтернатива — IronRDP (Rust, MIT/Apache-2.0). У него есть WASM-клиент и веб-компонент `@devolutions/iron-remote-desktop`, поддержка NLA через CredSSP/Kerberos и транспорт RD Gateway. Но для работы нужен шлюз, говорящий на RDCleanPath, то есть Devolutions Gateway ([IronRDP](https://github.com/Devolutions/IronRDP/blob/master/README.md); [Devolutions Gateway docs](https://docs.devolutions.net/gateway/knowledge-base/how-to-articles/launch-an-rdp-session-in-a-web-client)). Экосистема у него меньше, а условия бесплатного использования Gateway в заметках не проверены. Myrtille фактически заброшен: последний push был в марте 2024 года ([ecosyste.ms](https://awesome.ecosyste.ms/projects/github.com%2Fcedrozor%2Fmyrtille)).

Для SSH есть два варианта. Первый — использовать SSH-протокол того же Guacamole: SSH-сертификаты, SFTP, запись в typescript ([Guacamole: Configuring](https://guacamole.apache.org/doc/gug/configuring-guacamole.html)). Второй — собрать стандартную пару из xterm.js и WebSocket к бэкенду с SSH-клиентом. Эталоном такой схемы служит WebSSH2 (Node, ssh2, xterm.js, MIT) ([webssh2](https://redirect.github.com/billchurch/webssh2)). В MVP разумно не писать собственный терминал и пустить SSH через Guacamole. Тогда RDP и SSH получают единую модель токенов и записи. Приватные ключи хранятся только на сервере. Лучший вариант — короткоживущие SSH-сертификаты от внутреннего CA и закреплённые host keys. Это общая практика, в заметках она отдельным источником не подтверждена.

## AD — через LDAP с шифрованием, машины — через WinRM и JEA

Для операций с AD самый переносимый путь — прямой LDAP с шифрованием канала. Это может быть LDAPS 636, StartTLS или SASL bind через Kerberos с sign+seal. Основное ограничение: пароль в атрибуте `unicodePwd` можно изменить **только по 128-битному TLS- или SASL-шифрованному соединению**. Админский сброс делается одной операцией replace с новым паролем в кавычках в UTF-16LE. Если пароль нарушает политику, DC возвращает «Unwilling To Perform» ([Microsoft Learn: KB 263991](https://learn.microsoft.com/en-us/troubleshoot/windows-server/active-directory/set-user-password-with-ldifde)). В новых доменах Windows Server 2025 **подпись LDAP требуется по умолчанию**, так что simple bind на 389 сломается ([Microsoft Learn: LDAP signing](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/ldap-signing)). Это и так недопустимо. По библиотекам: `System.DirectoryServices.Protocols` в .NET работает и на Linux через libldap ([dotnet/runtime #110391](https://github.com/dotnet/runtime/issues/110391)), а Python ldap3 умеет `modify_password`, DirSync и persistent search ([ldap3 docs](https://ldap3.readthedocs.io/en/latest/microsoft.html)). Модуль PowerShell ActiveDirectory удобнее, у него готовые `Unlock-ADAccount` и `Set-ADAccountPassword -Reset`. Но он работает только под Windows и ходит в ADWS на TCP 9389 ([Microsoft Learn: ports](https://learn.microsoft.com/en-us/troubleshoot/windows-server/networking/service-overview-and-network-port-requirements)). Его место — внутри JEA-эндпоинта, а не в строковых скриптах, которые портал собирает на лету. Не проверено, проходит ли запись `unicodePwd` через SASL Kerberos sign+seal с не-Windows клиента. Microsoft говорит о «SASL encrypted» в общем виде, так что это надо проверить на своих DC.

Пароли Windows LAPS лежат в атрибутах объекта-компьютера. Microsoft «настоятельно рекомендует» включать шифрование. Оно идёт через CNG DPAPI с AES-256 и выполняется для **одного** принципала, поэтому доступ для нескольких ролей даётся через группу-обёртку. Права разделены на три кольца: управление сроком, чтение, расшифровка. Ротацию можно форсировать, сдвинув срок истечения, и устройство подхватит его в течение часа ([Microsoft Learn: Windows LAPS](https://learn.microsoft.com/en-us/windows-server/identity/laps/laps-concepts-overview)). Правильный сценарий в портале: показать пароль один раз после повторной MFA, сразу сдвинуть срок истечения на «сейчас» и записать событие в аудит. Расшифровку `msLAPS-EncryptedPassword` без PowerShell (например, из Linux) Microsoft не поддерживает. Это ещё один аргумент за Windows-воркер.

Для диагностики и действий на машинах (службы, процессы, журналы, диски, uptime, сообщение пользователю, logoff, перезагрузка) рекомендуемый Microsoft канал — **PowerShell Remoting через WinRM**, порты 5985/5986. По HTTP с Kerberos трафик шифруется AES-256 на уровне сообщений. По IP включается NTLM, который не подтверждает подлинность сервера ([Microsoft Learn: WinRM security](https://learn.microsoft.com/en-us/powershell/scripting/security/remoting/winrm-security)). Классический WMI через DCOM и RPC-инструменты требуют порт 135 плюс диапазон 49152–65535, который плохо закрывается брандмауэром ([Microsoft Learn: ports](https://learn.microsoft.com/en-us/troubleshoot/windows-server/networking/service-overview-and-network-port-requirements)). Поэтому CIM стоит гонять через WSMan, а `msg`/`logoff`/`quser` вызывать локально внутри WinRM-сессии. **JEA** — ключ к минимальным привилегиям. Эндпоинт работает от виртуального аккаунта или gMSA и разрешает только перечисленные функции, например `Send-UserMessage` или `Restart-ServiceSafe`. Каждая команда попадает в транскрипт, и подключающемуся не нужны права администратора ([Microsoft Learn: JEA](https://learn.microsoft.com/en-us/powershell/scripting/security/remoting/jea/overview)). Именно так устроен Windows Admin Center: шлюз на .NET 8/Kestrel управляет узлами через PowerShell и WMI поверх WinRM, а его RBAC разворачивает JEA-эндпоинт на каждом сервере ([Microsoft Learn: What is WAC](https://learn.microsoft.com/en-us/windows-server/manage/windows-admin-center/understand/what-is); [WAC user access](https://learn.microsoft.com/en-us/windows-server/manage/windows-admin-center/plan/user-access-options)). Эту схему стоит повторить у себя.

## Портал, который сбрасывает пароли, — это Tier 0

Microsoft прямо пишет, что WAC «не реализует, не отслеживает и не обеспечивает границу безопасности» ([Microsoft Learn: WAC user access](https://learn.microsoft.com/en-us/windows-server/manage/windows-admin-center/plan/user-access-options)). Самописный портал тоже её не обеспечит. Модель enterprise access требует «не допускать управления верхними плоскостями из нижних», а management и control planes названы «привлекательным путём для атакующих» ([Microsoft Learn: Enterprise access model](https://learn.microsoft.com/en-us/security/privileged-access-workstations/privileged-access-access-model)). Отсюда правило: **уровень портала равен высшему уровню объектов, которые он может изменить**. Если портал умеет сбрасывать пароль Domain Admin или читать LAPS контроллеров, то его хост, gMSA, база и CI относятся к Tier 0 и администрируются с PAW. Ставить такое на сам DC нельзя: даже WAC на контроллере домена не поддерживается ([Microsoft Learn: WAC install](https://learn.microsoft.com/en-us/windows-server/manage/windows-admin-center/plan/installation-options)). Практичнее разделить экземпляры или воркеры по уровням: helpdesk-портал для Tier 1/2 физически не может тронуть объекты с `adminCount=1`.

Есть две модели прав, у каждой свои риски. **Модель делегирования** (RBCD или KCD к WinRM/LDAP целей) позволяет выполнять действия от имени самого оператора, и атрибуция остаётся в журналах Windows. Но учётные записи из Protected Users делегировать нельзя ([Microsoft Learn: Protected Users](https://learn.microsoft.com/en-us/windows-server/security/credentials-protection-and-management/protected-users-security-group)). RBCD к тому же **всегда разрешает protocol transition** ([Microsoft Learn: KCD](https://learn.microsoft.com/en-us/windows-server/security/kerberos/kerberos-constrained-delegation-overview)). Украденный ключ gMSA портала позволит выдать себя за любого незащищённого пользователя на разрешённых целях ([The Hacker Recipes](https://www.thehacker.recipes/ad/movement/kerberos/delegations/constrained)), а право записи в `msDS-AllowedToActOnBehalfOfOtherIdentity` само становится примитивом захвата ([SpecterOps](https://specterops.io/blog/2018/10/25/another-word-on-delegation/)). **Модель «gMSA + RBAC в приложении»** проще. Пароль gMSA вычисляет DC, ручная ротация не нужна, а AES задаётся через `msDS-SupportedEncryptionTypes` ([Microsoft Learn: gMSA](https://learn.microsoft.com/en-us/windows-server/identity/ad-ds/manage/group-managed-service-accounts/group-managed-service-accounts/group-managed-service-accounts-overview)). Минус в том, что атрибуция держится только на журнале портала. Для MVP я рекомендую гибрид. Оператор входит в портал через Kerberos с MFA, авторизация выполняется в приложении. Воркер работает от gMSA своего уровня, и в AD ему делегированы **только** нужные права на конкретные OU: сброс пароля, `lockoutTime`, `userAccountControl`, `member` конкретных групп, чтение LAPS через группу-обёртку. Действия на машинах идут через JEA-функции портала. Тогда при компрометации приложения атакующий получит не больше, чем разрешают ACL в AD и JEA. Все привилегированные учётные записи нужно пометить «sensitive and cannot be delegated» или добавить в Protected Users. Список `PrincipalsAllowedToRetrieveManagedPassword` у gMSA должен состоять только из хостов портала.

Вход операторов делается через Windows Integrated Auth (Negotiate/Kerberos) плюс второй фактор на веб-уровне. Лучший второй фактор — WebAuthn/FIDO2-ключи, допустимы TOTP или Duo/privacyIDEA через ADFS. Kerberos здесь обязателен: если админы состоят в Protected Users, NTLM для них отключён по дизайну, а TGT живёт 4 часа ([Microsoft Learn: Protected Users](https://learn.microsoft.com/en-us/windows-server/security/credentials-protection-and-management/protected-users-security-group)). Форма с LDAP-bind заставит портал принимать открытые пароли админов, так что этого варианта следует избегать. У WAC MFA работает только через Entra, а on-prem есть лишь гейтинг по группам смарт-карт ([Microsoft Learn: WAC user access](https://learn.microsoft.com/en-us/windows-server/manage/windows-admin-center/plan/user-access-options)). Значит, MFA в своём портале придётся делать самим. Отдельно для админа на Mac: SSO Kerberos в Safari и Chrome требует TGT на Mac (`kinit` или Kerberos SSO extension). В заметках это не подтверждено источником, поэтому на старте нужен запасной вход через WebAuthn.

RBAC стоит описывать атомарными правами (`user.unlock`, `user.resetPassword`, `group.member.write`, `computer.laps.read`, `computer.session.shadow`, `computer.reboot` и т.д.) с областью «OU, набор групп, уровень». Для сброса пароля, раскрытия LAPS и записи в привилегированные группы нужны повторная MFA и поле «причина или тикет». Так же делают Devolutions, где для AD dashboard рекомендуют журнал с обязательным комментарием ([Devolutions docs](https://docs.devolutions.net/rdm/knowledge-base/how-to-articles/active-directory-dashboard-entry)). Аудит должен быть append-only и уходить с хоста в SIEM. Его дополняют транскрипты JEA, события shadow 20503/20504/20508 и записи сессий Guacamole. В LAPS Microsoft отдельно называет права на чтение и расшифровку «чувствительными» и требует их мониторить ([Microsoft Learn: Windows LAPS](https://learn.microsoft.com/en-us/windows-server/identity/laps/laps-concepts-overview)). Главный практический риск — веб-уязвимость, которая напрямую превращается в компрометацию домена. Поэтому нужны экранирование LDAP-фильтров, отсутствие PowerShell, собранного из строк (только параметры к фиксированным JEA-функциям), строгий CSP, anti-CSRF и доступ к порталу только из сети PAW.

## ASP.NET Core на Windows Server выигрывает у Linux-контейнера

Самый подходящий стек — **C#/.NET 8 или 10 LTS, ASP.NET Core и Blazor Server на доменном Windows Server 2022/2025**. Только здесь Windows-аутентификация, роли из AD-групп, имперсонация, PowerShell в процессе и прямые вызовы WTS работают без обходных путей. На Linux и macOS пакет `Microsoft.AspNetCore.Authentication.Negotiate` тоже умеет Kerberos, но для этого нужны домен, SPN, защищённый keytab из `ktpass` и `EnableLdap` ради получения групп. Сам Kerberos ролей не передаёт, а **имперсонация поддерживается только на Windows** ([Microsoft Learn: Windows Authentication](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/windowsauth)). У Negotiate есть ещё два подвоха: он не работает поверх HTTP/2 и ломается за обычным reverse proxy без привязки соединения 1:1 ([Microsoft Learn](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/windowsauth); [HAProxy discourse](https://discourse.haproxy.org/t/client-negotiate-haproxy-kestrel-debian-401/5751)). PowerShell встраивается через `Microsoft.PowerShell.SDK`, и ограниченный `InitialSessionState` сразу даёт каталог разрешённых действий ([Microsoft Learn: PowerShell hosting](https://learn.microsoft.com/en-us/powershell/scripting/developer/hosting/windows-powershell-host-quickstart)). Blazor Server держит всю AD-логику и секреты на сервере, а для админского инструмента это правильная граница. Python (ldap3 + pypsrp) и Go (go-ldap + masterzen/winrm с Kerberos) хорошо справляются с LDAP и WinRM ([pypsrp](https://pypi.org/project/pypsrp/); [masterzen/winrm](https://github.com/masterzen/winrm)). Но WTS из Linux им недоступен, и список сессий придётся получать разбором вывода `quser` через WinRM. Linux-вариант оправдан, только если в организации уже есть OIDC-провайдер (ADFS, Keycloak) и Windows-хост для воркеров.

PowerShell Universal остаётся быстрым путём: за 1–3 недели можно получить UI, RBAC, задания и историю на привычных скриптах. Но с 1 января 2026 года продукт принадлежит Devolutions. Windows-аутентификация, гранулярные права и терминалы в нём теперь лицензируются, лицензия годовая за каждый экземпляр, а бесплатная Developer edition **не может работать на серверах** ([Devolutions docs: Licensing](https://docs.devolutions.net/powershell-universal/licensing); [Devolutions blog](https://devolutions.net/blog/2026/02/powershell-universal-developer-edition-unlock-full-features-at-no-cost)). Реселлеры называют цену от $489.99, но актуальность для 2026 года не подтверждена ([ComponentSource](https://www.componentsource.com/product/powershell-universal/licensing)). PSU годится для прототипа на ноутбуке, но привязывать к нему Tier 0-инструмент с ежегодной подпиской менее выгодно, чем написать тонкий портал на .NET.

Целевая топология такая. Портал работает на отдельной доменной Windows Server VM (не DC) под gMSA, с TLS-сертификатом от внутреннего AD CS и SPN `HTTP/adcc.corp.local` на нужной учётной записи ([Microsoft Learn](https://learn.microsoft.com/en-us/aspnet/core/security/authentication/windowsauth)). Рядом стоит Linux-хост с guacd и guacamole-client в Docker. Третий элемент — Windows jump host (RDS) для shadow, на который каждый админ входит под собой. Если планируется публиковать mstsc как RemoteApp для нескольких админов, нужно отдельно проверить лицензирование RDS. Разработчику на macOS подойдёт такой цикл: C#-код пишется и запускается на Mac, AD и WTS скрыты за интерфейсами с моками, а интеграционные тесты Kerberos, WTS и JEA идут на Windows Server в UTM или Parallels в лабораторном домене.

## Поэтапный MVP-план на 10 недель

Сроки ниже — моя оценка для одного опытного разработчика. Опубликованных бенчмарков для подобных порталов найти не удалось. Порядок выбран так, чтобы самые рискованные вещи (shadow через jump host, Kerberos/SPN, права gMSA) проверялись раньше, чем написан UI.

| Этап | Недели | Что делаем | Готово, когда |
|---|---|---|---|
| 0. Лаборатория и инфраструктура | 1 | Лабораторный домен; GPO `Shadow=1` (контроль с согласием), правила SMB-In и «Remote Desktop - Shadow»; WinRM; gMSA с делегированием на тестовые OU; AD CS-сертификат; jump host с mstsc | `mstsc /shadow` с jump host работает; RemoteApp mstsc открывается через Guacamole с Mac |
| 1. Каркас портала | 2 | Blazor Server, Negotiate + роли из AD-групп, WebAuthn как второй фактор и запасной вход для Mac, append-only таблица аудита с выгрузкой в SIEM | Вход по Kerberos с Windows и по WebAuthn с Mac; каждое действие пишется в журнал |
| 2. Инвентарь и сессии | 3–4 | LDAP(S) или Kerberos sign+seal: OU-дерево, поиск, пагинация, кэш; WTS-опрос пулом с таймаутами; логон-скрипт «пользователь ↔ хост» | Поиск «где пользователь X» за секунды; список сессий RDS-серверов |
| 3. Подключения | 5–6 | Guacamole в Docker + encrypted JSON: RDP и SSH к серверам в один клик с записью; кнопка Shadow (сессия на jump host → RemoteApp `mstsc /shadow:<id> /v:<host> [/control]`); для Windows-админов — подписанный URL-обработчик | Админ на Mac делает shadow и RDP/SSH из браузера; события 2050x видны в аудите |
| 4. Управление AD | 7–8 | Разблокировка, сброс пароля (`unicodePwd`), включение и отключение, членство в группах, перенос между OU, раскрытие LAPS с немедленной ротацией; повторная MFA и тикет для чувствительных операций; запрет на объекты `adminCount=1` для helpdesk-ролей | Операции helpdesk выполняются без ADUC; права gMSA не шире делегированных OU |
| 5. Диагностика | 9 | JEA-эндпоинт с функциями портала: ping/DNS/порты, uptime, диски, службы, процессы, журналы событий, сообщение пользователю, logoff, перезагрузка | Типовой разбор «у пользователя тормозит» без RDP на машину |
| 6. Усиление | 10+ | Доступ только из сети PAW, разделение по уровням, CSP/anti-CSRF, алерты на LAPS-чтения и изменения привилегированных групп, пентест | Портал проходит ревью как Tier 0-актив |
| 7. Опционально | после MVP | MeshCentral для агентского «вижу экран» станций, если jump host неудобен или сеть не пропускает 445 и динамические порты | Shadow станций прямо в браузере без jump host |

Если пульт нужен немедленно, на 6–10 недель разработки есть мостик из готовых продуктов. Devolutions RDM (около $360 за пользователя в год) или Royal TSX (€49) дают подключения с Mac. На jump host ставится LizardSystems TSM Business ($299.95 за машину) для shadow, а для AD хватит RDM AD dashboard или бесплатного WAC ([Devolutions pricing](https://devolutions.net/pricing/); [Royal TSX](https://www.royalapps.com/ts/mac/features); [LizardSystems](https://lizardsystems.com/terminal-services-manager/purchase/)). Получится не «одно окно», но та же связка «Mac → jump host → mstsc» заранее проверит, устраивает ли команду такой UX shadow.

## Заключение

Главный вывод исследования: «единый пульт» — это в основном задача интеграции и безопасности, а не протоколов. Протоколы почти все уже есть: Guacamole для RDP/SSH, LDAP для AD, WinRM+JEA для машин. Единственный протокол, который нельзя ни купить, ни взять в open source в браузерном виде, — RDP shadow. Его клиентская часть недокументирована и живёт только в mstsc.exe, а попытки сделать её в FreeRDP стоят на месте с 2019 года. Поэтому писать собственный клиент `RpcShadow2` для MVP не стоит: это R&D без гарантий результата. Shadow нужно «доставлять» через Windows и сосредоточиться на том, что даёт реальную ценность: быстрый поиск сессии, один клик, аудит и согласие пользователя, которое задаётся политикой на конечной точке. Вторая неочевидная вещь: решение «писать самим» повышает ответственность. Портал с правом сброса паролей становится самым ценным объектом для атакующего после DC. Поэтому делегирование прав gMSA на OU и JEA важнее любого UI.

**Рекомендация.** Готовым берём Apache Guacamole (браузерный RDP/SSH, запись, encrypted-JSON токены), встроенный в Windows механизм `mstsc /shadow` на выделенном jump host, Windows LAPS, gMSA и JEA, а на будущее — MeshCentral для агентского доступа к станциям. Дописываем тонкий портал на ASP.NET Core + Blazor Server на доменном Windows Server. В нём будут Kerberos-вход с WebAuthn, инвентарь из LDAP, опрос сессий через WTS, кнопки RDP/SSH/Shadow, AD-операции через LDAP с шифрованием и делегированными правами gMSA, диагностика через JEA и append-only аудит в SIEM. MVP строим по плану выше примерно за 10 недель. Порядок такой: лаборатория и проверка shadow с Mac через jump host, затем инвентарь и сессии, подключения, операции AD, диагностика и усиление как Tier 0. На время разработки ставим мостик RDM/Royal TSX + LizardSystems TSM на jump host.
